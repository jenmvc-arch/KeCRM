每项教程都说明在哪里操作、本系统要配置什么，以及完成后如何验证。接入当天请再次以官方后台和文档显示为准。

SSupabase 数据库接入登录、数据表、权限与 CRM 在线数据7 步
官方操作参考数据库迁移 ↗API Keys ↗Row Level Security ↗
  1. 1
    建立 Supabase 项目

    在 Supabase Dashboard 建立一个专用于本 CRM 的项目，选择合适区域并妥善保存数据库密码。测试与正式环境建议使用不同项目，避免测试订单进入正式资料。

    完成后核对：项目状态为可用，并已明确谁负责 Dashboard 管理和备份。

  2. 2
    执行本系统的数据库迁移

    在 SQL Editor 完整运行 supabase/migrations/20260917_000001_flowtrace_initial_schema.sql；使用 Supabase CLI 的团队也可在已连接项目执行 supabase db push。迁移会建立客户、广告、来源历史、聊天、订单、AI 记录、Meta 队列、审计记录和 RLS 权限。

    完成后核对：SQL 没有报错，Table Editor 能看到 CRM 数据表，Database Advisors 没有未处理的高风险安全提示。

  3. 3
    取得浏览器可用的连接资料

    从项目的 Connect 对话框或 API Keys 页面复制 Project URL 与 sb_publishable_...。旧项目也可暂用 legacy anon key。不要复制 sb_secret_... 或 legacy service_role；这些高权限密钥会绕过 RLS，只能保存在服务端。

    完成后核对：手上只有 Project URL 和 publishable / anon key，没有把服务端密钥放进网页、Git、聊天或 CSV。

  4. 4
    配置邮箱登录规则

    在 Authentication 中启用 Email 登录并决定是否要求邮件确认。可以先在 Dashboard 建立老板账户，或稍后使用本页面的“创建账户”。若启用邮件确认，用户必须先完成验证才能登录。

    完成后核对：测试邮箱可以登录，未验证账户的行为符合公司的安全要求。

  5. 5
    在 CRM 保存配置并建立公司空间

    回到上方 Supabase 面板，填写 Project URL 和 publishable / anon key，点击“保存并测试”，再用邮箱登录。首次登录时填写公司名称和默认币种并建立公司空间；当前账户会成为老板。

    完成后核对：左侧状态显示“已连接”，页面显示 Supabase 在线数据；空数据库会明确显示暂无数据，不会混入本地模拟客户。

  6. 6
    验证老板与销售权限

    老板应能查看公司资料和保存业务规则；销售只能查看及修改分配给自己的客户。广告来源记录在浏览器端为只读，只能由受信任的 WhatsApp Webhook 服务写入，避免人工伪造广告或点击识别码。

    完成后核对：用老板和销售两个测试账户分别登录，确认销售无法看到未分配客户，也无法修改平台接入资料。

  7. 7
    保持演示保护，逐项接入服务端

    新公司空间默认使用演示运行模式，订单可以保存在 Supabase，但 Meta 外发会被数据库标记为已拦截。完成 WhatsApp Webhook、AI 服务、订单同步和 Meta 队列工作器后，再由管理员通过受控部署流程切换正式环境。

    完成后核对：演示订单没有发送到 Meta，所有真实平台密钥都只存在 Edge Function Secrets、Vault 或其他服务端 Secret Manager。

WWhatsApp Business 接入接收新咨询、保存来源、处理重复消息6 步
官方入门路径WhatsApp Cloud API 入门 ↗Webhook 配置 ↗
  1. 1
    先确认业务资产和负责人

    在 Meta Business Portfolio 中确认业务资料、WhatsApp Business Account 与业务号码由公司拥有，并让负责接入的人拥有所需管理员权限。准备一个用于联调的测试号码，避免上线时影响正在使用的销售号码。

    完成后核对：已明确业务资产负责人、号码归属和测试时间窗口。

  2. 2
    创建 Meta App 并添加 WhatsApp

    在 Meta App Dashboard 创建正式应用，选择当前的 WhatsApp 用例，在 Quickstart / API Setup 中关联或创建 WhatsApp Business Account。先使用测试号码和临时 token 收发一条测试消息；临时 token 会过期，不能作为正式环境凭证。

    完成后核对：已取得并记录 WhatsApp Business Account ID 与 Phone Number ID。

  3. 3
    为生产环境准备最小权限的服务端凭证

    由管理员按最新后台要求申请生产权限与 System User token。常见权限包括业务资产管理、WhatsApp 消息和 WhatsApp 业务管理相关权限；具体权限以接入当天 Meta 后台显示为准。凭证只写入服务端 Secret Manager 或环境变量。

    完成后核对：浏览器代码、CSV 导出、截图和应用日志中都没有 token、App Secret 或验证令牌。

  4. 4
    部署 HTTPS Webhook 并完成验证

    技术人员部署服务端回调地址，例如 POST /webhooks/whatsapp。在 Meta 后台填写 Callback URL 和 Verify Token；验证时 Meta 会以 GET 请求发送 hub.challenge 和验证参数，服务端只在 Verify Token 匹配时以 200 返回 hub.challenge。

    完成后核对：Webhook 页面显示验证成功，且生产地址支持 HTTPS。

  5. 5
    校验签名、订阅消息并写入 CRM

    接收 POST 后，服务端先以 App Secret 校验 X-Hub-Signature-256，再解析消息。用 WhatsApp 的外部消息 ID 去重、用规范化号码匹配客户；同一消息重复投递时只能更新互动记录，不能新建重复客户。广告来源能取得时保存历史，不能识别时保持“未知”。

    完成后核对：同一测试消息重复投递两次后，客户数和订单数都不增加。

  6. 6
    先做收消息验收，再决定是否开放发送

    用测试号码发起咨询，确认客户、聊天、负责人和首次来源都被正确记录。第一版仅让销售在 CRM 中查看或复制建议回复；即使正式接入完成，也不要默认自动向客户发送消息。日后若开放外发，还需单独处理模板、同意与业务规则。

    完成后核对：系统能接收、去重和审计，但没有任何自动外发动作。

MMeta 成交回传接入只发送符合成交标准的真实订单7 步
接入当天再次核对Business Messaging CAPI 官方文档 ↗
  1. 1
    先确认此业务场景能使用的事件和账户条件

    不要直接照演示页字段开发。先按 Meta 最新官方文档与 Events Manager / App Dashboard 核对 Business Messaging CAPI 当前支持的事件、必填字段、Marketing API Access Tier、数据集和权限。内部“合格客户”标签不是默认可发送的 Meta 优化事件。

    完成后核对：团队已记录计划发送的事件、目标资产、负责人和测试环境。

  2. 2
    确认资产归属并申请正确权限

    确认 Business Portfolio、WhatsApp Business Account、广告账户与 Dataset 的归属关系。Business Messaging CAPI 的 WhatsApp 侧通常需要 whatsapp_business_management 与 whatsapp_business_manage_events 等访问权限，后者可能需要在 App Dashboard 申请 Advanced Access；以当前后台审批结果为准。

    完成后核对：服务端凭证只能访问本公司获授权的 WABA、Dataset 和目标资产。

  3. 3
    创建或取得 Dataset，并只在服务器保存访问凭证

    按官方 Dataset API 创建或取得与该 WABA 对应的 Dataset ID。将 Dataset ID、服务端访问 token、环境名称和轮换负责人登记在部署配置中；token 不能填在此页面，也不能写入前端、导出文件或日志。

    完成后核对：测试与生产使用不同环境配置，且凭证可轮换。

  4. 4
    把“真实成交”定义成可审计的订单条件

    先在业务规则中选择“已付订金”或“已付全款”。只有订单编号唯一、金额和币种有效、付款达到标准且未取消/退款时，系统才建立 Purchase 待发送事件。AI 判断高意向、报价、预约或销售阶段“已成交”都不能代替真实付款记录。

    完成后核对：未付款的高意向客户不会出现在 Purchase 回传队列中。

  5. 5
    映射真实可取得的匹配资料

    服务端根据官方规则生成事件时间、金额、币种、WhatsApp Business Account ID 和其他允许的匹配资料。Click-to-WhatsApp 广告场景中，ctwa_clid 是广告点击进入会话时提供的唯一标识；没有它时要如实标记缺失，不能把内部 fb.* 值或猜测值伪装成 Meta 点击标识。

    完成后核对：缺少必要资料的订单会显示待处理原因，而不是伪造字段后发送。

  6. 6
    建立稳定事件 ID、去重和重试

    每笔订单建立稳定的内部幂等键和事件 ID。首次发送、网络失败后的重试和人工重复点击都必须复用同一标识；在发送前先检查订单与事件状态。CAPI 不会替本系统消除业务层的重复计算，因此订单去重必须由系统负责。

    完成后核对：同一订单重复保存或重试后，成交金额与回传记录只保留一笔有效事件。

  7. 7
    分别查看接收、归因与优化结果

    上线后需把三件事分开查看：CRM 保存的广告来源、Meta 接收事件的成功/失败状态、以及 Meta 实际归因和广告组的优化设置。事件接收成功不等于 Meta 已归因，也不代表已启用或保证成交优化。

    完成后核对：运营报表和账户优化结论均以 Meta 后台实际数据为准。

✦AI 分类服务接入提取资料、辅助判断，始终保留人工决定6 步
安全与生产实践OpenAI 生产实践指南 ↗
  1. 1
    先确定数据边界和审批责任

    明确可交给 AI 分析的数据范围、保存期限、访问人员和供应商数据处理要求。只传完成分类所需的信息，必要时先做脱敏；不要把客户聊天、号码或订单资料直接复制进公开工具。

    完成后核对：团队有可执行的数据处理说明和负责人。

  2. 2
    只从服务端调用 AI

    把 API key、模型名称、超时、重试次数和用量限制写在服务端环境变量或 Secret Manager。推荐将测试与生产分开配置，设置密钥轮换与权限边界。页面只显示连接状态，永不回显密钥。

    完成后核对：浏览器开发者工具、Git 仓库与导出文件都找不到 API key。

  3. 3
    先在“业务规则”写清楚判断标准

    维护产品、服务地区、最低预算和合格条件。服务端把这些规则与当前聊天一起传给模型，要求以固定结构返回需求、预算、地区、购买时间、质量建议、优先级、理由和聊天依据。

    完成后核对：规则变化后，新的分析记录能显示使用的规则版本。

  4. 4
    把聊天内容视为待分析资料

    聊天中的任何“忽略规则”“发消息给某人”或其他指令都不能改变系统行为。服务端应把聊天当作不可信资料，并限制模型只输出预先定义的字段；模型不能调用发送消息、创建订单或发送 Meta 事件的工具。

    完成后核对：包含指令式文本的测试聊天不会导致系统执行动作。

  5. 5
    用边界样本做验收

    至少测试合格、高意向未付款、不合格、来源未知、重复咨询和信息不足的案例。缺少预算、地区或购买时间等关键资料时，模型应返回“待了解”并列出要补问的内容，不要编造或强行判为合格。

    完成后核对：验收样本与人工复核结果被保存，便于后续改规则。

  6. 6
    保留人工审核和可追溯修改

    销售可采纳或修改 AI 建议，系统应记录修改人、时间、原值和新值。第一版只生成建议回复，销售确认后再手动发送；AI 不能自动改变成交状态或创建 Purchase 回传。

    完成后核对：每次人工修改都能在客户的跟进记录中追溯。

▣订单数据前置条件Meta Purchase 前必须完成的内部流程4 步
  1. 1
    选定统一成交标准

    管理层选择“已付订金”或“已付全款”作为可回传的成交条件，并把定义写入团队 SOP。不同销售不能各自理解“成交”。

    完成后核对：当前选择已被所有销售理解并能在订单录入时选择。

  2. 2
    完整录入真实订单

    每笔订单必须关联唯一订单编号、客户、金额、币种、付款达到标准的时间和来源。金额为零、订单编号为空或客户无法确认时，不能进入回传队列。

    完成后核对：重复订单编号被系统阻止，且记录可回查到订单凭证。

  3. 3
    同步取消与退款状态

    订单取消或退款后，立即更新 CRM 的订单状态，并从有效成交金额中排除。系统要保留历史，不应删除原记录；是否需要后续向外部平台处理，以正式接入当天的官方能力和业务规则为准。

    完成后核对：取消/退款订单不再出现在有效 Purchase 待发送队列中。

  4. 4
    先做重复操作演练

    在测试环境连续保存同一订单、重复点击发送、模拟网络超时再重试，确认订单、成交金额和回传事件均不会重复。通过后才开放生产回传队列。

    完成后核对：重复操作只会更新同一事件的状态，不会增加成交或收入。

上线前最后核对先验证测试号码、Webhook 去重、订单幂等、来源未知处理和失败重试；确认无误后才允许生产环境创建待发送事件。
